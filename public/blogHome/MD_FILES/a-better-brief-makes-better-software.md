# A better brief makes better software

The questions asked before implementation starts have a surprising effect on the quality of the finished product.

## Name the edges

A useful brief explains the goal, the audience, the constraints, and the moments where the normal path breaks. It gives a team something concrete to reason about.

```text
Goal -> user -> constraints -> states -> measure
```

Clarity at the beginning saves more time than speed at the end. It also creates a shared record for decisions that would otherwise be repeated.
